技术解读

AI 客服 Agent 的三大工程：Intercom Fin AI 与 Decagon 的架构拆解

以"用户有事去不了，要退票"为例，从架构到模块，从配置到运行时，完整拆解 AI 客服 Agent 的工程实现。
一、三大工程是什么

在 Agent 编程领域，构建一个 AI 客服产品涉及三层工程准备。每一层都有不同的模块在干活，最终把组装好的内容喂给 LLM。

工程一句话类比
Prompt Engineering给 LLM 写"说明书"——角色、规则、输出格式员工手册
Context Engineering给 LLM 塞"资料夹"——这一轮它能看到哪些信息工位上摆的文件
Harness Engineering给 LLM 装"操作系统"——流程编排、工具调用、转人工车间流水线控制室

这三者不是并列的"三个功能"，而是一次 LLM 调用之前的三层准备。

二、Intercom Fin AI 的模块拆解

以退票场景为例——用户说"我有事去不了了，要退票"。

2.1 Harness 层（编排控制）
模块退票场景中干什么
意图路由用户说"要退票" → 判断这是退款/取消意图，决定走 Custom Answer "退票流程"还是走自由对话
工具编排需要查订单时调用订单 API；用户确认后调用退款 API
护栏 & 人工转接退款金额 > 阈值？用户情绪激动？ → 转人工客服

Harness 不直接生成回复，它控制的是"流程"——要不要查订单、要不要调 API、要不要转人。它像一个状态机，每一步决定下一步往哪走。

2.2 Context 层（上下文组装）
模块退票场景中干什么
知识 RAG向量检索"退票政策"文章，命中"演出前 3 天内退 50%"
对话记忆管理历史轮次，如果用户第 2 轮才说"退票"，前文已有上下文
客户/订单数据通过用户身份 → 查 CRM → 查订单系统 → 拿到 #12345 ¥580

Context 层不决定说什么，它决定的是"LLM 这一轮能看到什么"。核心挑战包括：

  • Token 预算管理：知识库有 1000 篇文章，只能塞 3 篇进 prompt
  • 相关性排序：哪 3 篇最相关
  • 历史压缩：对话超过 10 轮后，前面的要摘要压缩
  • 数据注入时机：什么时候查订单（不是每轮都查）
2.3 Prompt 层（提示词组装）
模块退票场景中干什么
系统提示词"你是 XX 票务客服，帮助用户处理退票，遇到不确定的问题转人工..."
响应模板Custom Answer 里 Admin 写好的退票流程骨架（步骤 1 告知金额，步骤 2 确认，步骤 3 执行）
语气指令"友好、专业、简洁"，品牌口吻设定

Prompt 层不做决策，它负责把所有材料"排版"成 LLM 最容易理解、最不容易出错的格式。

三、Admin 配置什么——用户在 Fin 后台做的事

Fin AI 的核心设计理念是让非技术人员配置。Admin 在后台设置这 5 类东西：

1. 知识库文章

直接写/上传"退票政策"FAQ：

"演出前 7 天全额退，3-7 天退 50%，3 天内不可退"

这些文章会被向量化，供 RAG 检索。

2. Custom Answer

写一个"退票流程"的对话骨架：

"如果用户要退票 → 先查订单 → 告知退款金额 → 确认 → 执行"

这不是一个死流程，而是一个带条件的"建议路径"。LLM 会参考它但可以灵活变通。

3. Agent 人格

选择语气（友好/专业/俏皮），写品牌话术约束（"称呼客户为'您'"、"不要说'抱歉给您带来不便'"）。

4. API 工具

注册"退款接口"，定义输入参数（订单号、退款金额）和输出格式（成功/失败 JSON）。Fin AI 会用 function calling 调用。

5. 转接规则
"退款金额 > ¥1000 时转人工"
"用户连续 3 次表达不满时转人工"
"API 调用失败时转人工"

关键理解：用户配置的是"材料"和"规则"，不是代码。 三大工程负责把这些材料加工成 LLM 能理解的输入。

五、退票对话完整走一遍
图 2：退票对话逐步拆解——两轮对话中三大工程各模块的协作流程
Turn 1：用户发起退票

用户: "我有事去不了了，要退票"

Harness 层接收：

  1. 意图路由模块先用一次轻量 LLM 调用做分类 → 意图 = "退款/取消"
  2. 查 Custom Answer 列表 → 匹配到 Admin 配的"退票流程"
  3. 决策路径：先检索知识 + 查订单 → 再生成回复
  4. 护栏检查：不涉及敏感操作，可以继续

Context 层并行检索（Harness 批准后）：

  1. 知识 RAG → 向量搜索"退票政策" → 命中"3 天内退 50%"
  2. 客户/订单数据 → 通过 API 工具查 CRM + 订单系统 → 得到 #12345 ¥580
  3. 对话记忆 → 首轮，无历史

Prompt 层组装：把系统提示词 + Custom Answer 模板 + 检索到的知识 + 订单数据 + 用户消息，按固定结构拼成完整 prompt。

LLM 调用（一次）：

"我来帮您处理退票。您的订单 #12345 (演唱会票 ¥580)，距演出 3 天可退 50% 即 ¥290。确认退票吗？"

Harness 层后处理：检查回复 → 合规、未越权 → 推送给用户。

Turn 2：用户确认

用户: "是的，确认退票"

Harness 层：

  1. 意图路由 → 判断这是"确认执行"
  2. 工具编排模块触发 → 调用退款 API：refund(order_id="12345", amount=290)
  3. API 返回成功

Context 层：对话记忆记录了 Turn 1 的内容，无需重新检索知识。

Prompt 层组装：

[System Prompt + 人格] [对话历史: Turn 1 的完整记录] [工具执行结果: 退款成功 ¥290 已退回原支付方式] [指令: 告知用户退款成功] [用户消息: 是的，确认退票]

LLM 调用：

"退款已成功！¥290 将在 1-3 个工作日内退回您的原支付方式。还有其他可以帮您的吗？"
六、三层工程之间的关系——不是串行，是嵌套

这三层不是简单的串行流水线，而是嵌套协作：

图 3：三层嵌套关系——Harness 是外层循环，Context 和 Prompt 在其内部被调度
Harness 是"外层循环" ├── 每一轮对话，Harness 决定走什么流程 │ ├── 需要知识？→ 触发 Context 层检索 │ ├── 需要数据？→ 触发工具调用 │ ├── 需要回复？→ 触发 Prompt 层组装 │ │ └── → LLM 调用 │ ├── 回复合规？→ Harness 护栏检查 │ └── 需要转人？→ Harness 转接 │ └── 整个对话是多轮循环

具体关系：

  1. Harness 调度 Context：Harness 决定"这轮需不需要检索知识""需不需要查订单"，Context 负责执行检索并把结果返回。
  2. Context 喂给 Prompt：Prompt 层不自己检索任何东西，它只负责把 Context 层检索到的结果"排版"成 prompt 格式。
  3. Prompt 驱动 LLM：最终发给 LLM 的就是一个文本字符串，Prompt 层确保这个字符串结构清晰、信息完整、格式正确。
  4. Harness 检查 LLM 输出：LLM 返回后，Harness 检查是否合规、是否需要进一步行动（比如调用工具）。
七、Admin 配置 vs 系统自动——边界在哪
维度Admin 配置Fin AI 系统自动
知识库写/上传文章向量化、索引、检索
Custom Answer写流程骨架判断何时使用、填充动态数据
人格/语气选风格、写约束翻译成 system prompt 片段
API 工具注册接口、定义参数function calling、错误处理
转接规则写阈值/条件运行时评估、触发转接
对话记忆不需要管自动管理轮次、摘要、token 裁剪
RAG 检索不需要管自动向量搜索、相关性排序
护栏可选配置敏感词自动检查回复合规性

Admin 配的是"内容"和"规则"，系统负责"执行"和"编排"。 这是 Fin AI 这类产品设计的核心：让 Admin 像填表一样配置，系统在背后用三大工程把配置变成可运行的 Agent。

八、架构相同时的竞争关键是什么

两个产品都有 Harness + Context + Prompt 三层，都有意图路由、RAG、系统提示词——这就像两家餐厅都有厨房、灶台、菜单。有厨房不等于菜好吃。 竞争自然下沉到三个维度。

8.1 维度一：每层"做得有多深"
Harness 层——从"能调工具"到"调得聪明"
能力一般产品优秀产品
多步推理一步查一个东西链式推理：查A → 根据A查B → 根据B调C
错误恢复API 报错就卡住或转人工自动重试 → 换备选方案 → 降级回复用户
护栏精度全局开关"金额>0就转人工"分级：<¥100自动、¥100-1000需确认、>¥1000转人工

退票场景的差距：用户说"退票"，一般产品只能查到订单就回。优秀产品能在同一轮里完成：查订单 → 算退票金额 → 查退款政策 → 生成回复，用户只等一次。

Context 层——从"能检索"到"检索得准"
能力一般产品优秀产品
RAG 准确率召回 10 篇，3 篇相关召回 5 篇，4 篇相关（re-ranking 模型好）
Token 利用塞全文，浪费在废话上摘要 + 关键片段，同样窗口塞 2 倍信息
长对话记忆超过 10 轮就忘前面的压缩摘要 + 关键事实提取，20 轮还记得订单号
Prompt 层——从"能生成"到"生成得可靠"
能力一般产品优秀产品
Function calling参数格式准确率 85%99%（多次重试 + 格式校验 + 降级策略）
Few-shot 学习固定模板从历史高分对话中自动提取 few-shot 示例
输出一致性同样问题不同回复风格回复风格一致，符合品牌调性
8.2 维度二：层与层之间的"接缝"

这是最容易被忽略、但最拉开差距的地方。三层不是独立模块，它们的协作质量决定了整体效果：

Harness ↔ Context 的接缝：检索时机决策

  • 一般产品：每轮都全量检索（浪费 token、增加延迟）
  • 优秀产品：Harness 判断"这轮需不需要检索" → 用户说"好的"不需要检索 → 用户说"那退吧"需要查订单但不需要检索知识

Context ↔ Prompt 的接缝：上下文裁剪

  • 一般产品：RAG 返回什么就塞什么，prompt 膨胀
  • 优秀产品：Context 层做相关性打分，只把 Top-1 知识片段 + 订单数据塞进 prompt

Prompt ↔ Harness 的接缝：输出后处理

  • 一般产品：LLM 说啥就推啥给用户
  • 优秀产品：Harness 检查 LLM 输出 → LLM 幻觉说"全额退款" → 对比知识库发现政策是退 50% → 拦截，重新生成
8.3 维度三：工程之外的决定性因素
因素说明
Admin UX5 分钟配好 vs 2 天开发，决定谁能拿到非技术客户
数据飞轮100 万次对话 vs 1 万次，这是最难追的壁垒
生态集成预置集成多 = 切换成本高 = 客户留存
成本效率多模型路由 vs 单模型，决定定价空间

数据飞轮是终极护城河——架构可以抄、代码可以写、集成可以补，但一个做了 100 万次退票对话的产品，对边缘 case 的处理能力，是新入局者无论如何都追不上的。

九、Decagon 的架构——同骨架，不同肌肉

Decagon 的架构本质上也是 Harness + Context + Prompt 三层。差异不在"有没有"，而在每层做得有多深、层间接缝有多精细。

9.1 Harness 层——三个关键差异
① AOPs vs Custom Answers

两者解决同一个问题——"怎么让 Admin 告诉 Agent 该干什么"，但设计哲学不同：

Intercom Custom Answer 本质是"对话流程模板"。Admin 写一个流程骨架，LLM 参考它生成回复，但模板本身不是代码。

Decagon AOP（Agentic Operating Procedure） 本质是"自然语言写的可执行程序"。系统把自然语言编译成结构化逻辑，敏感步骤（检查天数、调退款 API）用代码执行，不让 LLM 自由发挥。

退票场景的实际差异：

  • Fin AI：LLM 生成回复 "您可退 ¥290，确认吗？" → LLM 也负责决定退多少（根据它看到的知识）→ 如果 LLM 幻觉，可能说错金额
  • Decagon：AOP 用代码算退款金额 (¥580 × 50% = ¥290) → 代码执行，不是 LLM 算的 → LLM 只负责把 ¥290 这个数字说出去 → 不会算错

这就是"代码级护栏"的含义——把"不能错"的部分从 LLM 手里拿走，用确定性代码执行。LLM 负责"对话"，代码负责"执行"。

② 多 Agent 架构 vs 单 Agent

Fin AI 基本是单 Agent，一个 LLM 调用处理意图识别 + 知识检索 + 回复生成。

Decagon 使用多个专门 Agent 分工：

  • 意图识别 Agent（轻量模型，快）
  • 知识检索 Agent（RAG 专用）
  • 系统调用 Agent（管 API）
  • 回复生成 Agent（大模型）
  • 情绪检测 Agent（监控用户情绪）
③ Supervisor model（实时监控）

Fin AI：回复生成后 → 基础护栏检查 → 推送

Decagon：回复生成后 → Supervisor model 独立审查 → "这个回复说全额退款，但知识库说退 50%？" → 拦截，重新生成

这是 Harness 层的"第二道防线"——不是一个护栏规则，而是一个独立的 LLM 审查另一个 LLM 的输出。

9.2 Context 层——两个关键差异
① 统一知识图谱 vs 基础 RAG

Fin AI：知识来源 = 帮助中心文章 → 向量检索，返回相关片段

Decagon：统一知识图谱 = 帮助文档 + 历史工单 + 连接系统的实时数据 → 不只是文本检索，是结构化知识图谱 → 能回答"这个用户上次退款是什么时候"这种需要关联数据的问题

退票场景：用户说"上次你们给我退了，这次怎么不行？"

  • Fin AI：检索"退票政策"文章 → 按当前政策回复 → 不知用户上次退过
  • Decagon：知识图谱关联用户历史 → 发现上次确实退过 → 查到上次是 7 天前退的（全额）→ 这次是 3 天内（50%）→ 回复"上次您在演出 7 天前退的，可以全额退。这次距演出只有 3 天，按政策退 50%"
② 多模型自动路由

Fin AI：所有步骤用一个模型（GPT-4 或 Claude）→ 意图分类也用大模型 → 贵且慢

Decagon：按步骤选模型 → 意图分类用小模型（$0.001）→ 知识检索用 embedding 模型 → 回复生成用大模型 → 自动选最合适的模型

成本差异：Fin AI 每轮 1 次 GPT-4 调用 = $0.03/轮；Decagon 意图分类用小模型 $0.001 + 生成用大模型 $0.02 = $0.021/轮。每轮省 30%，每天 10 万次 = 每天省 $900。

9.3 Prompt 层——情绪自适应语气

Fin AI：语气是静态的 → "友好专业" → 不管用户什么情绪都一个语气

Decagon：情绪 Agent 实时检测 → 动态调整 prompt 中的语气指令

  • 用户平静："您好，我来帮您处理退票..."
  • 用户愤怒："非常抱歉给您带来不便，我立刻为您处理..."

这不是两个模板，而是 Prompt 层根据 Context 层（情绪检测结果）动态修改语气指令。

10.3 Decagon 的深度优势在什么时候才真正拉开差距

是那 15-20% 的边缘 case——也是最容易让用户愤怒、最容易出事故的部分：

1. 需要跨系统关联的 case

用户说"上次你们退错了钱，这次别再出错"

  • Fin AI：检索退票政策 → 按政策回复 → 没查到上次退款记录
  • Decagon：知识图谱关联 → 发现上次退款确实有异常 → 主动处理

2. 需要多步确定性推理的 case

用户说"我买了 3 张票，退 2 张留 1 张"

  • Fin AI：LLM 算退款金额 → 可能算错
  • Decagon：AOP 用代码执行 → 精确算出每张的退费 → 不会错

3. 情绪敏感的 case

用户说"这已经是第三次了！！你们到底能不能解决！！"

  • Fin AI：正常语气回复 → 用户更怒
  • Decagon：情绪检测 → 调整语气 → 提升优先级 → 更快转人工

4. 需要回溯历史的 case

用户说"按上次那个方案处理就行"

  • Fin AI：不知道"上次那个方案"是什么 → 重新问
  • Decagon：对话记忆 + 客户历史 → 找到上次方案 → 直接执行
10.4 选型判断标准

选 Fin AI 的情况：

  • 客服 case 80%+ 是标准 FAQ 和简单流程
  • 团队没有技术资源做深度配置
  • 已有 Intercom 生态（Messenger + Inbox）
  • 预算敏感，要快速上线

选 Decagon 的情况：

  • 客服涉及多系统联动（订单 + 支付 + 物流 + CRM）
  • 退款/改签等不能算错的场景占比高
  • 客户体量大，1% 的错误率就是大量事故
  • 需要严格的可观测性和 A/B 测试能力
  • 有多渠道需求（chat + email + voice）
10.5 OTA 等高客单价行业的特殊考量

对 OTA（在线旅游）这类高客单价行业，一个关键判断是：那 15% 复杂 case 的自动化收益，不足以覆盖出错的风险成本。

情况AI 处理成本出错后修复成本人工直接处理成本
标准 3 天内退 50%$0.03 + 自动幻觉说全退 → 赔 ¥290¥5 人工费
多段行程部分退$0.05 + 自动算错退费 → 涉及航司协调¥8 人工费
联程航班取消改签$0.05 + 自动改错航段 → 客户滞留 → 投诉 + 赔偿¥8 人工费

OTA 的特殊性：一个 case 的交易金额可能是几百到几万，但一个错误 case 的赔偿成本是交易金额的几倍。 人工处理一个复杂 case 成本 ¥8，AI 出错后的修复成本可能是 ¥500-5000。

因此，对 OTA 来说，与其追求把 15% 也自动化，不如：

  1. 把 80% 简单 case 做到极致
  2. 把转人工做到丝滑（AI 已查到的信息无缝传给人工，不用客户重复说）
  3. 重视转人工衔接质量而非"多解决 5% 复杂 case"

在这个方向上，Fin AI 的性价比更高。

十一、总结

架构是入场券，不是护城河。

Intercom Fin AI 和 Decagon 都用 Harness + Context + Prompt 三层架构。差异在于：

  1. 每层的执行深度——同样叫 RAG，检索准确率差 20 个点
  2. 层间接缝的协作质量——Harness 能不能智能决定"这轮不检索"
  3. Admin UX——5 分钟配好 vs 2 天开发，决定谁能拿到非技术客户
  4. 数据飞轮——100 万次对话 vs 1 万次，这是最难追的壁垒
  5. 生态 + 成本——预置集成多 + LLM 调用便宜 = 定价空间和切换成本

Decagon 在工程深度上全面领先，Fin AI 在配置体验和生态成熟度上有优势。但对大多数能自动化的客服场景来说，Fin AI 的能力已经够用——真正的竞争焦点不是"谁能处理更多 case"，而是"谁能在 80% 的简单 case 上做到更低的单次成本 + 更好的体验 + 更丝滑的转人工衔接"。
